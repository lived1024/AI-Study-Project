## LLM 시스템의 특징
- **비결정론적 시스템**
  - 결정론적 시스템(deterministic) 
    - 같은 입력이 주어질 때, 항상 같은 출력 생성
    - 예시) 1 + 1 = 2
- 답변의 일관성을 해결하지 않고 내놓을 수 없음
- 일반적인 프로그래밍 언어보다 느리고 비싸다
- Single-turn, multi-turn : Save user session?
- 지속적인 유저 모니터링하며 업데이트
  - Data privacy, security, RAI ...

## LLM 디자인의 기본
### 1. LLM 사용 최소화
- 최대한 LLM 사용을 줄이고, 가능한 경우 결정론적 프로그래밍 언어 사용
  - 비용 절감 : LLM은 계산 비용이 많이 드는 반면, 결정론적 언어는 효율적
  - 속도 향상 : LLM 추론 속도는 느릴 수 있지만, 결정론적 코드는 빠르게 실행
  - 테스트 용이성 : 결정론적 코드는 테스트하기 쉽고, 디버깅도 용이
  - 유지 보수 용이성 : 결정론적 코드는 이해하고 유지 관리하기 쉬움

### 2. 처음부터 확장성 및 안정성 고려
- 시스템 설계 단계부터 확장성과 안정성을 고려해야 함
  - 느린 속도 : 확장성이 없는 시스템은 사용자 증가 시 속도 저하
  - 높은 비용 : 안정적이지 않은 시스템은 유지 관리 비용 증가
  - 예측 불가능한 결과 : 시스템 출력 결과가 매번 다를 경우 신뢰도 저하
  - 서비스 제공 시 중요 : 상용 서비스로 제공하려면 확장성과 안정성 필수
- 안정적인 API 디자인
- Load balancing, Auto scaling, Circuit breaker 패턴 고려

### 3. 응답 품질의 확실한 테스트
- 특히 민감한 분야(의료, 정부, 법률, 금융) 시스템 응답 품질을 엄격하게 테스트해야함
  - 부정확한 정보 : 잘못된 정보 제공 시 심각한 결과 초래 가능
  - 편향된 결과 : 특정 그룹에 대한 편향된 결과는 차별로 이어질 수 있음
  - 비윤리적 결과 : 사회적 문제 야기 가능
  - 법적 책임 : 잘못된 정보로 인해 법적 책임 발생 가능성
- A/B 테스트, 사용자 피드백 수집, 지속적인 모니터링 필요

### 4. RAI, 데이터 개인 정보 보호, 보안 고려
- 책임 있는 AI(RAI), 데이터 개인 정보 보호, 보안은 LLM 시스템 설계 필수 요소
  - 윤리적 문제 : 편향, 차별, 악용 등 윤리적 문제 발생 가능성
  - 개인 정보 침해 : 개인 정보 유출 시 심각한 결과 초래 가능
  - 시스템 해킹 : 보안 취약점 악용 시 시스템 손상 및 데이터 유출 가능성
- 데이터 암호화, 접근 권한 관리, 감사 로그 등 보안 체계 구축

### 5. 운용 비용 고려
- 파인 튜닝, RAG 시스템, 그 외 모든 LLM 관련 비용이 상상이상으로 비쌈
- 수익 모델을 먼저 고려하고 도입
- Token 사용량, API 호출 빈도, 인프라 비용 등 세밀한 비용 분석 필요

## LLM 디자인 간소화하기
### **Single turn** vs **Multi turn**
- LLM 시스템 설계 시 싱글턴 또는 멀티턴 방식 선택 고려
  - Single turn : 한번의 요청으로 응답 생성
  - Multi turn : 여러 번의 요청과 응답 교환을 통해 응답 생성
- 선택 기준
  - 작업 유형
    - Single turn : 간단한 작업 (번역, 요약, 단답형 질문 등)
    - Multi turn : 복잡한 대화 (상담, 문제 해결, 창작 작업 등)
  - 데이터 양
    - Single turn : 적은 양의 데이터
    - Multi turn : 많은 양의 데이터
  - 사용자 경험
    - Single turn : 빠른 응답
    - Multi turn : 자연스러운 대화

### 데이터 소스 숫자 줄이기
- 너무 많은 데이터 소스는 시스템 복잡도 증가
- 핵심적이고 신뢰할 수 있는 데이터 소스만 선별
- 데이터 품질 > 데이터 양
- 실시간 데이터 vs 배치 데이터 구분하여 처리
- 사용자 세션 관리
  - 시스템에서 대화 내용을 저장할 지 여부 결정해야 함
    - 저장 시 이점
      - 사용자 경험 개선 : 이전 대화 기반 개인 맞춤형 응답 제공 가능
      - 모델 학습 데이터 활용 : 저장된 대화를 모델 학습 데이터로 활용하여 성능 향상
      - 문맥 유지 : 연속된 대화에서 문맥 이해도 향상
    - 저장 시 단점
      - 개인 정보 보호 문제 : 대화 내용에 개인 정보 포함 시 문제 발생 가능성
      - 저장 공간 및 처리 비용 증가
    - GDPR, CCPA 등 개인정보 보호 법규 준수 필요

### Caching, Async, Data Simplification
#### **Caching 전략**
- **응답 캐싱**
  - 동일하거나 유사한 질문에 대한 응답을 캐시
  - Redis, Memcached 등 인메모리 캐시 활용
  - 캐시 유효 기간(TTL) 설정으로 최신성 보장
  - 비용 절감 효과 : 반복적인 LLM 호출 방지

- **벡터 임베딩 캐싱**
  - RAG 시스템에서 자주 사용되는 문서 임베딩 캐시
  - 임베딩 계산 비용 절약
  - 검색 속도 향상

- **프롬프트 템플릿 캐싱**
  - 자주 사용되는 프롬프트 패턴 미리 준비
  - 동적으로 변수만 교체하여 사용

#### **비동기 처리 (Async)**
- **비동기 API 설계**
  - Long-running 작업은 비동기로 처리
  - Webhook이나 폴링을 통한 결과 전달
  - 사용자 경험 개선 : 긴 대기 시간 방지

- **백그라운드 작업**
  - 배치 처리로 대량 데이터 분석
  - 스케줄링된 모델 업데이트
  - 로그 분석 및 성능 모니터링

- **스트리밍 응답**
  - 실시간으로 응답 생성 및 전송
  - 사용자가 응답을 기다리는 시간 단축
  - WebSocket, Server-Sent Events 활용

#### **데이터 단순화 (Data Simplification)**
- **전처리 최적화**
  - 불필요한 데이터 제거
  - 텍스트 정규화 (소문자 변환, 특수문자 제거)
  - 중복 데이터 제거

- **토큰 수 최적화**
  - 프롬프트 길이 최소화
  - 핵심 정보만 추출하여 전달
  - Context window 효율적 활용

- **구조화된 데이터 활용**
  - JSON, XML 등 구조화된 형태로 데이터 정리
  - 파싱 오류 최소화
  - 일관된 응답 형식 보장

## 모니터링 및 개선
### 성능 지표 추적
- **응답 시간** : 평균, 최대, 95 퍼센타일
- **토큰 사용량** : 입력/출력 토큰 수, 비용 계산
- **오류율** : API 오류, 타임아웃, 품질 이슈
- **사용자 만족도** : 피드백 점수, 재사용률

### 지속적인 개선
- A/B 테스트를 통한 프롬프트 최적화
- 사용자 피드백 기반 모델 튜닝
- 새로운 기술 및 모델 도입 검토
- 비용 대비 성능 분석

## 결론
LLM 시스템 설계는 단순히 모델을 선택하고 API를 호출하는 것이 아니라, 전체 시스템의 아키텍처, 비용, 보안, 사용자 경험을 종합적으로 고려해야 하는 복잡한 작업입니다. 
- **데이터 중심 설계**로 시작하여
- **최소한의 LLM 사용**을 원칙으로 하고
- **확장성과 안정성**을 고려하며
- **지속적인 모니터링과 개선**을 통해
성공적인 LLM 시스템을 구축할 수 있습니다.
